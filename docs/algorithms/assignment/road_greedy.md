# RoadGreedy：取货点分组与有界候选归并

类别：assignment。选择 ID：`road_greedy`。

[返回算法目录](../README.md) · [公共协议与参数规则](../common.md)

实现见 [RoadGreedy](../../../algorithms/assignment/standard.py)，结果对照与最大规模测试见 [Greedy 回归](../../../tests/test_assignment_busy.py)。候选筛选和堆维护属于分配算法，框架内核独立校验并提交提案。

## 分配规则

只考虑可接单车辆和 pending 任务，按以下排序键逐个选择：

```text
有向取货距离 → 车辆 ID → 任务发布时间 → 任务 ID
```

在场车辆从当前位置计算距离，停车车辆从所属停车区出口计算；不可达的组合不进入候选。距离只衡量到 pickup 的道路步数。该算法是 Greedy matching，不保证全局总距离最小。

## 分组字典与共享候选

`groups` 是以取货点 ID 为 key 的 Python dict，value 是该点的任务列表，每组按 `(release_tick, task_id)` 排序：

```text
groups[A] = [T1, T2]
groups[B] = [T3]
```

取货点对应字典键和任务组；hash table 的 slot/bucket 是底层存储概念，不等同于取货点。分组让同一起点到同一取货点的距离只查询一次。

`starts` 按可用车辆的起点格点 ID 分组。共享停车出口的车辆具有相同的任务距离排序，因此共用一个候选列表，不为每辆车复制全部取货点候选。

令 V 为可接单车辆数、P 为 pending 任务数、S 为不同车辆起点数，设置 K = min(V, P)。每个起点只保留按 `(distance, release_tick, task_id)` 排序最优的 K 个可达任务。

## 为什么只保留 V 个任务仍然精确

固定一辆车，其完整候选按 `(distance, release_tick, task_id)` 排序。轮到它接单前，其他车辆最多完成 V−1 次分配，最多消耗 V−1 个不同任务。

因此：

- 若它至少能到达 V 个任务，最优 V 个中必然至少剩一个未分配任务。排在 V 名以后的任务不会先于这个剩余候选被选中。
- 若可达任务不足 V 个，保留全部可达任务即可。
- 同一起点的车辆具有相同的候选排序，可以共享列表；全局比较时仍分别加入各自的车辆 ID。

所以按可用车辆数确定的保留数量不会改变完整配对排序的结果。它不是可随意调小的近似截断参数。

## 筛选阶段：每个起点一个临时最大堆

`pools[start_id]` 在筛选时用最大堆保留最优 K 个任务。Python heapq 提供最小堆，因此代码保存取负的键：

```python
(-distance, -release_tick, -task_id)
```

这样堆顶对应当前保留集合中最差的原始候选：

1. 未满 K 个时加入新任务。
2. 已满且新任务更优时，替换堆顶。
3. 已满且新任务不更优时，停止扫描这个取货点的后续任务。

第三步成立，是因为同一个取货点组的距离相同，任务已经按发布时间和 ID 排序；后面的任务不可能更优。

筛选完成后，把每个 pool 按取负键逆序排序，得到原始键从优到劣的列表。列表本身保留取负的值，避免复制所有候选元组；插入全局堆时恢复原值。

## 分配阶段：一个全局最小堆

`queues[vehicle_id]` 指向该车辆起点的共享候选列表；全局 `candidates` 堆每辆车最多保留一个当前候选：

```python
(distance, vehicle_id, release_tick, task_id, index)
```

前四项执行分配排序；`index` 是该车辆在共享列表中的位置。不同车辆共享列表内容，但独立推进自己的 index。

每次弹出：

- 任务尚未使用：记录 `result[vehicle_id] = task_id`，把任务加入 `used`。这辆车不再入堆。
- 任务已被其他车辆选走：向后跳过 `used` 中的任务，把下一个可用候选重新入堆；列表耗尽则不再入堆。

更新候选后必须重新入堆比较，不能直接分配，因为其他车辆可能有更优候选。全局堆中每辆车始终最多一个候选，因此不需要保留大量同车候选并在接单后逐个清除。

例如两辆车都把 A 组 `[T1, T2]` 排在 B 组 `[T3]` 前面，K=2：

```text
V0 候选列表：[T1, T2]，距离均为 1
V1 候选列表：[T1, T2]，距离均为 3

初始全局堆：V0—T1、V1—T1
弹出 V0—T1：分配，used={T1}，V0 不再入堆
弹出 V1—T1：T1 已使用，推进到 T2，把 V1—T2 重新入堆
弹出 V1—T2：分配，结束
T3 继续等待
```

这里略去 T3 仍然精确，因为两辆车总共最多使用两个任务。

## 什么时候维护，保留多少个堆

内核每 tick 调用一次 `assign()`；没有可接单车辆时立即返回，不扫描任务或计算距离表。需要分配时：

1. 建立本次任务分组与车辆起点分组。
2. 筛选阶段维护 S 个容量不超过 K 的临时最大堆。
3. 最大堆排序后成为共享列表，再建立一个最多 V 项的全局最小堆。
4. 分配完成后释放这些分组、列表和堆，下 tick 根据新快照重新建立。

| 状态 | 含义 | 生命周期 |
| --- | --- | --- |
| `groups` | 各取货点的有序任务列表 | 本次调用 |
| `starts` | 各起点的可用车辆列表 | 本次调用 |
| `pools` | 各起点筛选堆，随后原地排序成共享列表 | 本次调用 |
| `queues` | 车辆 ID 到共享列表的引用，不复制列表 | 本次调用 |
| `candidates` | 每辆车最多一个当前候选的全局堆 | 本次调用 |
| `used`、`result` | 已使用任务及最终分配 | 本次调用 |
| `self.cache` | 有向 BFS 距离表，预算来自资源配置 | 跨 tick，地图改变时释放旧缓存 |

不同世界有独立算法实例，不共享这些可变运行状态。

## 候选规模与复杂度

令 G 为不同取货点数，K=min(V,P)：

- 完整配对最多保留 VP 项，旧的车辆/取货点堆最多保留 VG 项。
- 当前保留的任务候选最多 SK 项，全局堆最多 V 项。S 不超过 V，因此上界为 V×min(V,P)+V，与取货点数 G 不直接相乘。
- 512 辆车共用一个停车出口时，最多保留 512 个任务候选和 512 个归并堆项；即使覆盖最大地图的全部 8640 个取货点，也不建立约 442 万个配对元组。
- 512 辆车分散在 512 个不同起点时，最多保留 262144 个任务候选和 512 个归并堆项。Python 对象仍有内存开销，该数量边界不等于字节预算。

不含图搜索时，建组与组内排序最坏 O(P log P)；筛选最坏检查 SP 个任务候选，最大堆更新为 O(log(K+1))，筛选完成后的列表排序为 O(SK log(K+1))。每辆车在列表中最多推进 K 项，归并最坏 O(VK log(V+1))。实际可以在取货点组内提前结束扫描。

这是用有限的筛选计算换取明确的候选空间上界，不保证所有小场景都比旧实现更快。任务分组、候选列表和距离缓存的内存应分别衡量。

## 距离搜索与缓存上限

S <= G 时，从每个不同车辆起点做正向 BFS；否则从每个取货点做反向 BFS。共享停车出口时只需一个起点表。两种方向计算相同的有向最短距离，不改变分配排序。

框架按地图复用正向和反向邻接表，只包含可通行格点。距离表使用紧凑整数数组，算法实例按 LRU 保留，数组数据预算由 [资源配置](../../../config/resources.py) 的 `DISTANCE_CACHE_MIB` 指定，默认 128 MiB。单表超过预算时仅供本次查询使用，不保留。该预算不包含拓扑、任务分组和候选列表。

若地图有 N 个可通行格点、E 条有向边，每次未命中的 BFS 为 O(N+E)，每张距离数组占 N 个整数。一次冷缓存分配最多搜索 min(S,G) 个端点；缓存不足时仍可能重算。

## 参数与边界

当前没有额外算法参数。候选保留数量由 V 推导；内存预算和车辆数量范围在 [配置目录](../../../config/README.md) 修改。放货点、未来道路占用和出库排队时间不进入当前排序键。算法只提交分配提案，由内核再次校验。
