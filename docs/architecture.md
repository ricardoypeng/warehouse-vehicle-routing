# 框架与状态边界

实现入口：[实体模型](../framework/backend/domain.py)、[算法接口](../framework/backend/contracts.py)、[CPU 内核](../framework/backend/cpu/engine.py)。

## 实体与引用

- `Map` 持有 `Cell`、`Road` 和停车区对象；格点通过只读 neighbors 引用相邻格点，通过 road 引用单向路。
- `Vehicle.cell` 引用当前位置，`Vehicle.current_task` 引用当前任务；任务的 assigned_vehicle 反向引用执行车辆。
- `Task.pickup`、`Task.dropoff` 和计划中的 Cell 都必须是地图持有的原始对象，不能复制或来自其他世界的地图。
- `World.occupancy[cell_id]` 直接引用占用车辆。格点没有第二份可变 occupant 字段。
- `MovementPlan` 仅保存 deque[Cell]，没有规划或决策方法。队首是下一步，不包含当前位置；队首等于当前位置表示显式等待一 tick。
- `Shelf` 与 `AccessPoint` 是静态地图展示对象：货架引用其格点，存取点引用所属货架和真实道路格点；不引入库存状态。
- `execution_state` 只表示停车、取货途中、取货、放货途中、放货、空闲、返场阶段，由内核维护。

地图结构冻结，动态世界分开；可以共享同一 Map，但车辆、任务、占用表和算法状态均应独立。

## 移动提交

内核先验证所有计划更新，全部合法后才安装。算法返回的计划会复制为每辆车独立的剩余步骤队列，避免不同车辆共享可变队列。

每 tick 的执行顺序：

1. tick 加一，发布任务，分配算法提出匹配，校验后提交。
2. 空闲无任务车设置返场目标，已经到入口的车入库。
3. 捕获本 tick 已在装卸的车辆集合。
4. 规划算法读取只读世界快照，提出替换或清空计划。
5. 小车读取计划队首；空计划等待。
6. 仲裁同格竞争、交换和停止队列传播。先释放全部获准移动的原格点，再写入目标占用和车辆位置。
7. 成功移动后出队；显式等待执行后出队；移动被拒绝时不推进计划。
8. 已在装卸的车消耗服务时间；其他到达目标的车辆开始服务。
9. 停车区按队列与出车间隔出库。刚出库本 tick 不再移动。
10. 更新执行反馈、连续无移动计数并检查引用与占用一致性。

服务结束后清空旧计划。卸货完成的任务保留 assigned_vehicle 历史引用，小车 current_task 清空，下一个 tick 才重新分配。取货服务结束后，下一 tick 算法为放货目标更新计划。零服务时间在到达时完成相应状态切换。原地接单时，取货到达时间记录为本次接单的当前 tick；车辆已经位于取货点，因此允许在本 tick 消耗装货服务时间，不将事件时间回拨到上一 tick。

默认地图包含 29×14 格、48 条单向路、126 个存取点和四角无限停车区。单向道路容量共 216，不包含路口。每 tick 每车最多沿合法有向边前进一步，每格最多一车；允许跟进和长度至少三的合法同步环，禁止两车交换。

## 只读算法输入

WorldView 含只读映射、不可变 VehicleView/TaskView 和静态地图，不暴露真实 Vehicle/Task。现有计划转为 tuple 供读取，last_results 给出上次请求、实际移动和阻塞原因。

实际更新只能通过 AssignmentUpdates、PlanUpdates 和内核。Python 只读接口用于防止普通误修改，并不作为不可信代码的安全隔离边界。

## 统计和结束

任务全部卸货完成且全车入库才 finished。仅累计无移动 tick 不证明死锁。连续无移动计数只统计本 tick 移动阶段的在场运输车辆；停车区排队、入库和出库都不影响这些车辆的计数。没有在场运输车辆或至少一辆成功移动时清零。

道路占用在移动前采样。道路上至少一辆运输阶段车辆未移动，该路增加一个堵塞 tick；主动等待也计入。装卸占用格点但自身不算交通等待。首次出库排队单列，不计主要累计等待；再次出库排队计入。

新增评价与容量判据应明确统计口径。批量输出保留 finished、完成任务数、tick、任务 hash 和实际后端，避免用未完成场景宣称更快。

## CPU / CUDA

[CPU 计算接口](../framework/backend/cpu/compute.py) 与 [CUDA 计算接口](../framework/backend/cuda/compute.py) 提供相同 score 操作。CUDA 可用时执行 float64 矩阵评分；不可用或运行出错后转 CPU。结果状态始终报告 requested、effective 和 fallback_reason。

[计算后端协议](../framework/backend/contracts.py) 定义 ComputeBackend 的 validate、score、info、设备元数据和可选的 `tensor_entry()`。算法与内核依赖该协议，具体实现无需继承 CPUBackend；后端工厂负责选择 CPU 或 CUDA 实现。`tensor_entry()` 只把 tensor runtime 与设备分发给算法，路由和矩阵求解仍由算法自己实现；CPU 后端返回 None，CUDA 后端只在实际设备为 cuda 时返回入口。MatrixRoutes 未获得外部后端时仍创建默认 CPU 评分器。

参数解析报告由 Registry 根据原始输入生成，在构造 Engine 时传入，保留被忽略参数和默认值回退的原因。直接构造 Engine 而未提供报告时，parameter_report 为 None，表示没有注册器解析上下文；不能仅凭最终配置恢复原始调整记录。

当前不是 GPU 仿真器，不能以评分加速代替端到端加速结论。未来新增 CUDA 操作必须先提供 CPU 语义和一致性测试。

## 载货与展示数据

Vehicle.is_loaded 和 cargo_state 由当前任务与执行阶段推导，不另存一份可能失步的载货标志。取货服务中为空载，服务结束进入 to_dropoff 后载货，dropoff 卸货服务中仍载货，卸货完成后空载。Task 的历史 cargo_state 在完成后固定为 delivered，不随执行车辆的新任务改变。

静态地图输出货架范围、货架编号和存取点编号；动态快照输出载货状态、服务剩余时间、实际剩余计划、停车区数量及任务时间记录。前端使用这些真实状态绘制，不用随机或装饰性货物标记。

批量步进在请求范围内聚合所有事件，并通过 `event_records` 保留原始 tick；只生成一次最终状态快照，不丢弃中间事件。命令行无界面运行仍只在结束时序列化状态。

## 运行时隔离与恢复

[ProcessEngine](../framework/process_engine.py) 让一个独立 spawn 进程持有完整世界、canonical 实体和算法实例。HTTP、run 和 batch 均通过它执行；直接构造 CPU Engine 属于同步底层接口。

默认 30 秒没有完成 tick 的进展报告时，控制器终止并回收 worker。启动初始化也有相同期限。长批次定期报告已完成 tick，持续推进不会因总耗时超过期限而被误杀。`--runtime-timeout` 可调整期限。

失败后 HTTP 保留最后一次完整返回的快照及失败原因，后续步进返回 409；重置会创建新 worker。删除、重置及关闭服务会回收原 worker。首个世界选择与快照构建受管理锁保护，快照和步进受会话锁保护；取得锁后会重新检查指定世界是否仍有效。其他页面替换世界后，旧页面收到 404 会重新连接第一个世界。

TaskView 为不可变快照，未变化任务可复用对象；状态或关联改变时生成新对象。车辆和占用映射分别构建；任务映射在没有变化时可复用，有变化时复制后替换条目，旧快照不会观察到后续更新。HTTP 当前仍返回完整任务列表，大场景网络和渲染开销需单独衡量。

## 通用工具

[framework/utils](../framework/utils/) 保存框架与算法共同使用的基础工具：[图搜索与有界距离缓存](../framework/utils/graph.py)、[静态路口距离与路线展开](../framework/utils/junction.py) 和 [任务指纹](../framework/utils/fingerprint.py)。内核从此处导入通用工具，不依赖算法包。算法侧的 [兼容导出](../algorithms/common.py) 保留已有 `path`、`distances_to` 导入方式。具体的任务分组、候选堆、路线多样性和评分规则仍属于各算法；MatrixRoutes 自建压缩路口图和私有 min-plus 距离矩阵，不读写共享路口缓存的距离表。静态路口缓存按地图共享 V×V 距离表和路线展开表，表行用紧凑数组存储，规划器只读取 `distance()`；`route()` 保留给需要完整路线的调用方和测试，当前内置规划器不使用。两张表合计 12·V² 字节加行开销，规模由场景 rows/columns 上界限定，最大布局约 5.2 MiB/地图；按最大会话数同时驻留时额外内存上限约 670 MiB，不参与可调预算配置。MatrixRoutes 不写入这两张共享表，而是每个实例自建压缩路口图和私有 V×V 距离矩阵（最大布局约 3.5 MiB/实例），这部分实例内存不计入上面的共享缓存上界。表在首次规划查询时懒构建，`serve`/`run` 的首个 tick 会计入一次性建表成本；基准与比较工具在初始化阶段预构建。

每 tick 分配前扫描任务并复用未变化的不可变 TaskView；规划阶段复用这份任务映射，只对本次分配改变的任务复制映射并更新条目。车辆位置、执行状态和计划重新快照，以包含分配与出入库变化。旧任务映射与旧快照不会被修改。每 tick 保留完整不变量检查，性能优化应先测量快照、检查和寻路的开销，保持旧快照的独立性与批量提案校验语义。

框架资源预算和运行默认值统一从 [根配置目录](../config/README.md) 导入。场景 dataclass 继续负责校验和序列化，其默认值和范围来自共享配置。前端通过设置 API 使用相同的场景范围，避免前后端分别写死数值。
