# MatrixRoutes：矩阵计算候选与评分

类别：planning。选择 ID：`matrix_routes`。

[返回算法目录](../README.md) · [公共协议与参数规则](../common.md)

实现位于 [matrix_routes 包](../../../algorithms/planning/matrix_routes/__init__.py)：[压缩路口图](../../../algorithms/planning/matrix_routes/_graph.py)、[私有矩阵距离表](../../../algorithms/planning/matrix_routes/_distance.py)、[CPU 矩阵求解器](../../../algorithms/planning/matrix_routes/_solver.py)、[tensor 求解器](../../../algorithms/planning/matrix_routes/_tensor.py)、[全局移动集合诊断](../../../algorithms/planning/matrix_routes/_diagnosis.py)、[算法主体](../../../algorithms/planning/matrix_routes/_planner.py)。CUDA 设备入口由计算后端通过 `tensor_entry()` 分发，矩阵路由计算完全在算法内完成。

## 什么时候选择路线

车辆必须在地图上、有目标，且处于 TO_PICKUP、TO_DROPOFF 或 RETURNING。当前计划为空，或连续等待达到 `replan_wait` 时，算法重新选择路线；其他车辆不重新选路线，若不在本次诊断的移动集合中，规划器只在其计划前插入等待步。

## 候选生成与缓存

按 `(起点格点 ID, 目标格点 ID)` 缓存候选集合。同一地图下再次遇到相同起终点时，若候选仍在 LRU 缓存中则复用；更换地图时清空缓存并释放压缩图结构。

首次生成时：

1. 第 1 条候选由算法私有的 min-plus 矩阵距离表贪心重建静态最短路；它不读取共享的 [JunctionCache](../../../framework/utils/junction.py)。
2. 之后每一轮把当前惩罚矩阵 \(p\) 转成压缩路口图上的代价，并做一次批量 min-plus 值迭代。对每个路口节点 \(j\) 和每一行 \(r\)，同步执行

\[
V_r(j) \leftarrow \min_{(j\to k)\in E}\bigl(V_r(k) + \text{steps}(j\to k) + \text{penalty}_r(j\to k)\bigr),
\]

其中 `penalty_r(j→k)` 是这条边进入的格点在 \(p\) 中的惩罚之和。道路边按“道路格点 + 出口路口”计费，块移动按“目标路口”计费；落在道路上的终点追加一条固定前缀边。值迭代以目标节点为 0，迭代到不再变化；同步 sweep 最多需要路口数轮。
3. 收敛后按 `argmin` 方向的 backpointer 矩阵从起点节点回溯出节点路径，再拼回道路格点、起点道路后缀和终点道路前缀，得到 Cell 元组。
4. 把本轮路线经过的每个格点在 \(p\) 上累加 `diversity_penalty`，供下一轮矩阵变贵；无论本轮路线是否重复都累加。

因此候选 0 是静态最短路，后续候选是在当前惩罚矩阵下的惩罚加权最优路线，可以为减少重复格点而绕行。惩罚进入矩阵求解的代价，不进入公共 `path()` 的 \(g\)，也不改变其他规划器的语义。所有缓存未命中的起终点在同一次 `update` 中逐轮批量求解；同一轮内不同行的目标节点、惩罚矩阵和终点前缀各不相同。

最终不同候选数最多为 `candidate_count`，不保证恰好达到该数量，也不保证是全局前 K 条最短路线。`diversity_penalty = 0` 时不执行后续候选轮次，候选集合只含首条静态最短路。起点不可达目标时抛出包含起终点 ID 的异常，终止本次规划，不把不可达路线当作 0 分候选；HTTP 世界进入失败状态，批量作业记录错误。

### 私有矩阵距离表

算法按地图自建压缩路口图，并维护一张**实例私有**的路口距离矩阵，不写入框架共享缓存：

- 距离表用 min-plus Floyd–Warshall 计算：
  \[ D_{ij}\leftarrow\min(D_{ij},D_{ik}+D_{kj}) \]
- 有 tensor 入口且路口数达到内部阈值时，用 torch 在设备上按 k 循环批量更新矩阵；小图用纯 Python 参考实现；大图且无 tensor 时回退到算法私有的逐路口加权搜索。
- 候选 0 从距离表出发，沿使“边步数 + 目标行距离 = 当前行距离”成立、且边序号最小的后继重建路线。
- 距离矩阵规模为 \(V\times V\)，最大地图 676 路口约 3.5 MiB，随地图对象一起在实例内缓存，更换地图时释放。

## 特征与评分

为本次需要规划的车辆汇总所有候选，每条候选形成一行特征：

```text
[路线步数, 路线上被其他车辆当前占用的格点数]
```

占用特征在每次评分时根据当前快照重新计算，不随候选路线一起缓存。评分为：

\[
\operatorname{score}(r)
= \operatorname{distance_weight}\,|r|
+ \operatorname{occupancy_weight}\,\operatorname{occupied}(r)
\]

其中 \(|r|\) 为路线步骤数，`occupied(r)` 为路线中被其他车辆占用的格点数。两个权重的比值决定是否值得绕行：若候选比静态最短路多走 \(\delta\) 步、少经过 \(\Delta\) 个被占用格点，则只有 `occupancy_weight` × \(\Delta\) 大于 `distance_weight` × \(\delta\) 时才会选更长的那条。每辆车选择自己候选中得分最低的一条，替换当前移动计划；得分相同时保留候选生成顺序中最早的一条。

## 全局移动集合诊断

候选评分仍是逐行计算，但“下一 tick 哪些车可以同时移动”不是逐车能决定的问题：默认地图上 40 车时，每辆车的最短路前方都被别的车占住，内核每次仲裁都无法同时放行任何一辆，逐车重新规划只会反复选中同一条最短路，40 车 seed 0 在 tick 3000 时仍停在 164 个完成任务。算法因此在评分之后增加一层对全车队一次性求解的矩阵诊断，实现见 [_diagnosis.py](../../../algorithms/planning/matrix_routes/_diagnosis.py)。

记活动车辆槽位集合为 \(S\)，\(P\) 为位置矩阵（槽位数 × 格点数）、\(D\) 为目标矩阵（每辆车请求的下一格点）、\(C = D P^{\top}\) 为声明矩阵：\(C_{ij}=1\) 表示槽位 \(i\) 请求槽位 \(j\) 当前占用的格点。内核接受一次同步移动的条件是：每个目标格点空闲或被另一辆已接受的车让出；没有两辆车请求同一格点；没有两辆车直接交换格点；长度 ≥3 的环允许整体旋转。诊断正是对 \(C\) 求这些规则的矩阵闭包：

1. **闭包层：** \(C\) 的每一行至多一个 1（每辆车只请求一个格点），所以声明矩阵是一个函数式有向图：闭包分解为互不相交的环和通向环的尾链。用一条指针遍历加路径标记即可在均摊 O(1) 每槽位内找到所有环，不需要稠密传递闭包。只有长度 ≥3 的环作为种子，因为内核会整体旋转它们；两车交换永不作为种子。
2. **传播层：** 环上的槽位直接整体接纳；其余槽位由“目标空闲或目标被已移动车辆占用”逐层接纳。每个目标格点只保留一个请求者，优先级复刻内核：等待更久的车辆优先，再按确定性轮转顺序。依赖层级恰好是链长（链长 \(k\) 在第 \(k\) 层被接纳），实现用一个队列按依赖顺序处理：空格点先接纳其最高优先级请求者，已进入移动集合的车辆让出格点后再接纳该格点的最高优先级请求者，每个槽位只检查一次，总代价 \(O(V)\)。通向停住车辆或通向被拒交换的链永远不会被接纳。
3. **掩码层：** 不在移动集合中的活动车辆由规划器在计划前加一个“原地等待”步骤。把被阻塞的请求者屏蔽掉，正是环能够旋转的原因：这些请求在内核仲裁前就消失，环不再死于声明冲突。被屏蔽者原本也无法移动，因此不损失推进量。掩码后这些车辆在内核结果里的 `blocked_reason` 是 `planned_wait` 而不是 `node_conflict` 或 `occupied_by_stopped_vehicle`，它们自身的等待累计与原本受阻时一致；全队 `stalled_ticks`、`moving` 统计的是实际推进，会随诊断把环转起来而变化，这正是诊断生效的表现。前端按 `blocked_reason` 显示的受阻提示会相应变成按计划等待。

诊断只预测内核在掩码后请求集合上的移动仲裁，不预约未来格点，也不改变候选评分；内核仍是唯一校验和裁决方，若仲裁规则变化，诊断必须同步修改。声明矩阵的稀疏结构让闭包退化为一次 O(V) 指针遍历，传播也只需一次 O(V) 队列遍历（V 为活动车辆数，上限 512），远低于一次 tensor 启动开销，因此固定在 CPU 上执行；tensor 入口仍用于距离矩阵与候选值迭代。

实测默认地图、`road_greedy`、1000 任务、3000 tick 预算：加入诊断前 40 车的 seed 0/1/2 在预算内分别只完成 164、577、714 个任务；加入诊断后三个 seed 均在 895–897 tick 完成全部任务。同批 81 次对比运行（27 个独立配置 × 3 次重复，重复只提供计时样本）中 MatrixRoutes 通过 27/27，拥堵率 1.74%，而 Traffic-aware 为 24/27、4.90%，ShortestPath 为 15/27、9.04%。车数极限工具在同一地图和任务集上测得 40–400 车的 15 个档位（每档 3 个 seed、4000 tick 预算）全部 3/3 通过：40 车中位完成 tick 896，200 车 790，400 车 890；诊断只负责解开逐车评分看不到的同步死锁，完成 tick 仍由车数与任务节奏决定。更大布局上，medium 场景（6×6、64 车、1000 任务）三个 seed 都在 3000 tick 预算内完成，maximum 场景（12×12、512 车、10000 任务）800 tick 推进到 771 个完成任务。

## 与全局算法、局部算法的对比

同一默认地图、`road_greedy`、1000 任务、CPU 后端下的对比：MR 为本文的 MatrixRoutes，另有全局算法与局部算法作为对照。每档 3 个 seed，每个 trial 独立子进程；复现命令见 [算法对比工具](../../benchmarks.md#算法对比与车数极限)。

| 场景组 | MR | 全局算法 | 局部算法 |
| --- | --- | --- | --- |
| 20/30/40 车，3000 tick | 9/9，拥堵 1.74%，仿真中位 3.21 s | 9/9，2.23%，2.02 s | 9/9，2.22%，1.89 s |
| 40/50/60 车，4000 tick | 9/9，完成 tick 896/777/709 | 9/9，908/791/727 | 8/9，60 车 seed 1 未完成（981/1000） |
| 80/100 车，4000 tick | 6/6，完成 tick 650/697 | 1/6，80 车仅 seed 0 在 681 tick 完成 | 2/6，80 车 seed 0/1 完成（692/860 tick） |

MR 的完成 tick 在 40–60 车与全局、局部接近或略低；代价是每 tick 的候选矩阵求解加诊断开销，20–60 车纯 CPU 仿真中位慢约 1.5–1.9 倍。80 车起全局、局部开始无法全部完成，100 车两者均为 0/3；MR 在 80/100 车仍 3/3 完成。80/100 车组的拥堵率 MR 为 9.7%/15.5%，全局算法为 37.3%/44.1%，局部算法为 30.3%/48.1%；未完成的运行把中位仿真时间显著拉长（80 车全局/局部 34.7 s、2.7 s，100 车 98.5 s、27.9 s，MR 为 4.7 s、7.2 s）。

## 参数

| 参数 | 类型 | 默认值 | 允许范围 | 作用 |
| --- | --- | ---: | --- | --- |
| `candidate_count` | int | 6 | 1–32 | 候选生成的搜索轮数，也是不同候选数量上限 |
| `replan_wait` | int | 3 | 1–10000 | 连续等待达到多少 tick 后重新选择路线 |
| `diversity_penalty` | float | 1.0 | 0–1000 | 后续候选在矩阵代价中累加到已用格点的惩罚 |
| `distance_weight` | float | 1.0 | 0–1000 | 路线步数的评分权重 |
| `occupancy_weight` | float | 0.25 | 0–1000 | 当前占用格点数的评分权重 |

参数解析、错误回退和应用方式见 [公共规则](../common.md#可配置参数)。两个评分权重同时为 0 时，所有候选同分，选择最早生成的一条。

## CUDA 设备入口

框架的计算后端只负责选择实际设备并分发 tensor 入口：`ComputeBackend.tensor_entry()` 返回 tensor runtime 与设备，或在没有设备运行时返回 `None`。规则见 [计算后端协议](../../../framework/backend/contracts.py)。

- 算法在需要且值得使用 tensor 时领取一次入口；CPU 后端返回 `None`，此时使用纯 Python 参考实现。私有距离表在路口数达到内部阈值时也领取同一入口；候选求解按“行数 × 边数 × 节点数”阈值决定是否使用 tensor，避免小图上启动开销超过计算本身。
- CUDA 后端只有在实际设备为 `cuda` 时返回入口；torch 批量求解见 [tensor 求解器](../../../algorithms/planning/matrix_routes/_tensor.py)。设备回退到 CPU 时不返回入口，算法直接走参考求解器，不隐式在 CPU 上跑 torch。
- 全局移动集合诊断不领取 tensor 入口：声明矩阵每行至多一个 1，闭包是一次 O(V) 指针遍历（最大 512 车），在 CPU 上远低于一次 tensor 启动开销，与候选求解按工作量阈值切换设备的规则一致。
- tensor 求解抛异常时，当前实例后续候选生成改用 CPU 参考求解器，并把原因记录在算法实例的 `routing_fallback_reason`；快照中的 `backend` 字段描述评分后端，不单独报告算法内路由回退。
- 框架不实现路由、不决定矩阵求解的回退，只提供设备入口。

## 边界与成本

候选求解等价于压缩路口图上的 Bellman 值迭代，最坏轮数不超过路口数，同步 sweep 的每一轮是 \(O(E)\)。每次候选生成需要 `candidate_count − 1` 轮求解，缓存未命中时才有这部分开销。maximum 场景实测中跨路口缓存未命中的批次通常只有 1–4 行，单次值迭代的 sweep 次数主导耗时：maximum 地图 200 tick 的 `update` 耗时 CPU 约 16.0 s、CUDA 约 15.7 s，CUDA 的主要收益在私有距离表的一次性矩阵构建，而不是这些小批次候选求解。私有距离表在首次候选生成时构建：Floyd–Warshall 为 \(O(V^3)\)；默认地图 64 路口低于 tensor 阈值 128，实际走 CPU 纯 Python（约 7 ms）；medium 196 路口和 maximum 676 路口才领取 tensor 入口，预热后中位约 10 ms 和 47 ms，CPU 回退在 medium 约 173 ms、maximum 改用私有逐路口搜索。候选缓存只约束跨调用保留的路线；压缩图、私有距离矩阵、每轮临时矩阵和 tensor 张量另占内存。

每辆车先按自己的候选独立评分，再由全局诊断统一决定下一 tick 的移动集合；两者都不预约多 tick 的未来格点，不改变内核的校验和裁决职责。当前占用不等于未来占用，候选评分本身不保证完成率；诊断消除的是“所有车同时请求被占格点”造成的永久死锁，不保证任意布局、车数或预算下都能完成。全局诊断每次调用做一次 \(O(V)\) 环检测和一次 \(O(V)\) 队列传播（\(V\) 为活动车辆数，上限 512；实测 512 车约 1.7 ms/次），相对候选矩阵求解的开销可以忽略，CPU 回退路径同样执行。CUDA 矩阵求解与评分也不等于整个仿真在 GPU 上运行。默认参数沿用加入全局诊断前标定的距离/占用权重比例（1 : 0.25），加入诊断后的 81 次对比直接用这组默认值通过 27/27；没有在诊断之后重新调参。

## 候选缓存预算

候选集合以不可变 tuple 保存，按 [资源配置](../../../config/resources.py) 的 `MATRIX_ROUTE_CACHE_MIB` 限制，默认 128 MiB。LRU 计费包括键、路线容器、条目包装和索引增长；Cell 由地图共享，不重复计费。固定空缓存对象开销不计。预算不足时淘汰最久未使用的起终点组合；单个集合超预算时不保留，但仍参与本次评分。命中会续期，淘汰只影响重新生成的计算量，不改变该起终点的确定性候选生成与评分规则。

缓存预算只约束跨调用保留的数据。本次批量规划中尚需评分的候选、压缩图、矩阵求解临时值和输出计划另占内存。
